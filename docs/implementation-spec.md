# 오션스펍 매장 관리 구현 명세

## 1. 구현 범위

관리자가 저장한 경기, 미션 달성, 별 지급을 여러 기기에서 공유한다. 매장 TV의 손님 화면은 로그인 없이 공개 가능한 닉네임과 집계만 보여준다. 관리 기능은 로그인한 직원만 사용한다. 현재 GitHub Pages 목업의 사용 흐름을 이어가되, 저장과 권한 확인은 서버로 옮긴다.

| 경로 | 화면 | 접근 |
|---|---|---|
| `/admin` | 게임 결과·경기 기록, 게임 종류, 회원, 매장 통계, 빙고, 월간 미션, 별, 프라이즈 지급 | 관리자 |
| `/guest` | 주간 랭킹, 월간 빙고, 월간 미션, 별 랭킹, 전체 화면 | 공개 조회 |
| `/login` | 초대받은 관리자 로그인 | 공개 진입 |

운영 배포에서 `/admin.html`과 `/guest.html` 요청은 새 경로로 연결한다. 기존 GitHub Pages는 목업 확인용으로 유지한다. 운영 도메인과 현재 Pages 도메인이 다르면 기존 페이지에 운영 링크를 안내한다.

## 2. 화면과 업무 규칙

### 경기 입력과 기록

- 게임 종류는 신규 등록과 수정이 가능하다. 초기 종류는 첫 게임, 데일리, 딥랭크, MTT다. 순위마다 랭킹 점수, 바인권 수량, 오션스 티켓 수량을 독립적으로 입력한다. 빈 순위는 각각 0이다. 프라이즈가 없는 경우도 지원한다.
- 초기 배점은 첫 게임 0점, 데일리 1위 2점·2위 1점, 딥랭크 1위 5점·2위 3점이다. 이후 순위는 0점이다. MTT의 실제 배점과 프라이즈는 운영자가 설정한다. 목업의 임시 MTT 배점을 운영 기본값으로 가져오지 않는다.
- 경기일, 종류, 참가 회원, 순위를 저장한다. 닉네임 검색은 기존 회원을 먼저 보여주고, 일치 회원이 없으면 신규 등록을 명시한다. 앞뒤 공백을 제거하고 유니코드 NFC 정규화 후 닉네임의 대소문자를 무시해 중복을 막는다. 경기 저장에 실패하면 신규 회원도 함께 롤백한다.
- 순위는 터치로 선택하며, 이미 사용 중인 순위를 고르면 두 참가자가 맞교환된다. 목록은 순위 오름차순으로 즉시 정렬한다. MVP는 1위부터 연속 순위, 한 경기 내 회원·순위 중복 금지로 처리한다.
- 경기 기록은 날짜 내림차순 그룹으로 접고 펼친다. 경기별 순위·닉네임·점수·프라이즈를 표로 표시하고 기록에서 날짜·종류·참가자·순위를 수정한다. 저장 후 주간 랭킹과 회원·매장 통계를 다시 계산한다.
- 경기는 저장 당시 점수·프라이즈 규칙 버전을 참조한다. 같은 게임 종류로 기록을 정정하면 기존 규칙으로 새 순위에 보상을 계산하고, 게임 종류를 바꾸면 새 종류의 현재 규칙을 적용한다. 과거 규칙 복원이 불가능한 이관 기록은 확인된 보상만 입력한다. 이미 지급한 프라이즈는 지급 시점의 스냅샷으로 보존하고, 정정으로 자격이나 랭킹이 바뀌면 관리자에게 표시한다.

### 주간 랭킹

- 기준 시간대는 Asia/Seoul이다. 경기일 기준 월요일부터 일요일까지의 양수 점수를 회원별로 합산한다. 동점은 공동 순위로 표시한다. 예시 순위는 1, 1, 3이다. 0점 회원은 주간 랭킹에 나오지 않는다.
- 지급 대상은 해당 주 순위가 1~5위인 회원이다. 공동 5위도 포함한다. 종료된 주차의 지급을 기본으로 하고, 과거 주차를 선택할 수 있다. 지급 중복 방지 단위는 회원당 주차당 1회다. 시즌 또는 월 경계와 별개로 주차 식별자는 월요일 날짜를 사용한다.

### 월간 빙고

- 월별 3×3 보드에 미션 9개와 3줄·올빙고 프라이즈를 설정한다. 관리자 화면에서 월·칸별로 달성 회원을 등록하거나 취소한다.
- 가로·세로 각 3줄과 대각선 2줄을 계산한다. 3줄 이상과 9칸 완성은 별도 단계로 지급 대상에 오른다. 지급된 단계는 같은 월·회원 기준으로 중복 지급할 수 없다.
- 게스트는 선택한 월의 칸별 미션과 달성 닉네임을 본다. 해당 월 빙고 지급 기록이 있는 닉네임은 금색과 지급 완료 범례로 표시한다. 20명 이상이면 줄바꿈하고 칸 높이를 늘려 표시한다.

### 월간 미션

- 공통 템플릿에 여러 미션을 한 번에 등록한다. 입력 개수 상한은 두지 않는다. 새 미션은 이번 달 및 이후 월에 사용할 수 있으며 과거 월에 확정된 미션과 기록은 보존한다.
- 월별 화면에서 각 미션의 달성 회원을 기록·취소한다. 회원 요약은 완료한 서로 다른 미션 수, 각 단계의 지급 대상 및 지급 완료 여부를 표시한다. 다음 달에는 템플릿을 재사용하고 달성 기록은 새로 시작한다.
- 지급 기준은 **1개·4개·5개**다. 단계별 프라이즈 이름은 관리자 설정이다. 5개를 달성하면 1·4·5개 단계 각각이 지급 가능하며 기존에 받은 단계는 제외한다. 월별 지급 기록에 프라이즈 이름을 복사한다.
- 게스트는 해당 월의 미션별 달성 닉네임과 단계별 프라이즈를 본다. 해당 월 월간 미션 지급 기록이 있으면 닉네임을 금색으로 표시한다.

### 별 모으기

- 별 지급용 미션은 이름만 등록한다. 지급할 때 회원·미션을 선택하고 개수를 입력한다. 삭제한 미션은 지급 선택에서 숨기고 기존 이력에는 지급 시점의 이름을 유지한다.
- 누적 잔액은 월별로 초기화하지 않으며 20개 상한도 두지 않는다. 게스트는 최다 잔액부터 1개까지 내림차순으로 표시하고, 동일 개수의 회원은 같은 그룹에 배치한다. 0개 회원은 숨긴다. 큰 범위는 페이지를 나눠 전체 구간을 탐색할 수 있게 한다.
- 별 20개 이상인 회원에게 프라이즈를 지급하면 20개의 차감과 지급 이력이 한 번에 저장된다. 40개인 회원은 서로 다른 두 번의 지급이 가능하다. 기간이 바뀌어도 기존 잔액과 지급 이력은 유지한다.

### 프라이즈 지급

- 관리 화면에 주간 랭킹, 월간 미션, 빙고, 별의 지급 대기 목록을 분리한다. 주간 기준일과 월간 기준 월을 선택할 수 있다. 별은 현재 잔액 기준이다.
- 각 행에 회원, 자격, 프라이즈 이름, 기준 기간을 표시한다. 실제 수령 이후 지급 버튼을 사용하며 서버가 최신 자격을 다시 계산한다. 지급 이력은 지급자, 지급 시각, 기준 기간, 근거, 프라이즈, 차감 내역을 보존한다. 지급 대상 계산과 이력에는 경기 결과에서 직접 획득한 바인권·오션스 티켓을 중복 포함하지 않는다.
- 지급 기록은 변경 이력을 남기기 위해 원본 행을 보존한다. 운영자 정정이 필요한 경우 사유를 포함하는 별도 취소 이벤트를 사용하고, 별 지급 취소는 동일 트랜잭션에서 20개 복구를 기록한다. 취소한 지급 건의 재지급은 다시 자격을 검사한다.

### 회원 관리와 매장 통계

- 관리자 회원 화면에 전 회원을 표시한다. 이번 주·이번 달 버튼과 시작일·종료일 직접 선택을 지원한다. 참가 횟수는 기간 내 경기 수, 승률은 1위 경기 수 ÷ 참가 수, 평균 상위 비율은 경기별 (순위 ÷ 기록된 참가자 수)의 산술 평균이다.
- 바인권과 오션스 티켓은 획득 개수를 합산한다. 인머니는 프라이즈를 하나 이상 받은 경기 수 ÷ 전체 참가 경기 수다. 한 경기에서 두 프라이즈를 받아도 인머니 1회다. 참가가 0이면 비율은 대시로 표시한다.
- 방문은 경기 기록이 있는 날짜의 수다. 같은 날 여러 경기에 참가해도 1일이며, 마지막 방문일은 전체 경기 기록 기준이다. 경기 참가 없이 실제로 방문한 손님을 집계하려면 별도의 체크인 기능이 필요하다.
- 매장 통계는 일간·주간·월간 기간 조회, 전체 경기 수, 참가 회원 수, 진행일 수, 게임 종류별 횟수, 날짜별 추이, 회원별 참가·방문 횟수, 상세 표를 제공한다. 차트에 수치와 표를 함께 제공한다.

### 손님 화면

전체 화면 진입·종료와 탭 전환을 지원한다. 풀스크린 API 미지원 브라우저에서도 일반 화면을 사용할 수 있다. TV에서 이름을 읽을 수 있도록 닉네임을 감싸며, 회원이 많은 상태를 1080p와 모바일에서 검증한다. 갱신 시 현재 탭과 선택 기간을 유지한다. 공개 응답에는 내부 회원 ID, 관리자 ID, 방문·승률 통계, 비공개 지급 이력을 포함하지 않는다.

## 3. 저장소 선택

| 항목 | 관리형 PostgreSQL | Google 스프레드시트 |
|---|---|---|
| 참가·순위·프라이즈 정합성 | 유니크 제약, 외래 키, 트랜잭션으로 강제 가능 | 애플리케이션 검증과 수정 경로 통제가 필요 |
| 별 차감·지급 기록 | 한 트랜잭션에서 잔액 잠금, 자격 검증, 기록 가능 | API 일괄 쓰기는 가능하나, 동시 자격 확인과 직접 셀 편집까지 관리하기 어려움 |
| 월·주·일 조회와 회원 집계 | SQL 집계, 인덱스, 기간 검색 지원 | 수식과 피벗으로 시작 가능하며 데이터 구조가 커지면 유지 비용 증가 |
| 접근 권한 | 서버에서 관리자 쓰기·공개 조회 범위 분리 | 시트 공유 권한과 앱 권한을 별도로 관리해야 함 |
| 운영 | 마이그레이션, 백업, 복구 점검 필요 | 수동 입력과 내보내기가 쉬움. API 쿼터와 공유 설정의 영향을 받음 |

**권고는 PostgreSQL을 기록 원본으로 사용하고, 스프레드시트는 CSV 내보내기로 활용하는 것이다.** 여러 관리자가 동시에 별 프라이즈 지급 버튼을 누르는 경우에도 잔액과 이력이 맞아야 하고, 게임을 정정해도 이전 보상 규칙과 지급 이력을 재현해야 한다. 이 두 조건을 DB 트랜잭션 및 제약으로 검증할 수 있다. POC 수준의 단일 운영자·수동 집계라면 시트로 시작할 수 있지만, 현재 기능을 운영하려면 시트에 별도의 동시성·권한·감사 로직을 다시 만들어야 한다.

구현 기본안은 **Next.js + TypeScript + Supabase(PostgreSQL 및 Auth)**다. 운영 앱은 서버 기능을 제공하는 호스팅에 배포하고, 후보 기본값은 Vercel이다. UI는 기존 화면의 한국어 용어와 작업 흐름을 재사용한다. 인증된 쓰기는 서버를 통과하고, 공개 화면은 서버가 가공한 응답만 읽는다. 초기에는 15초 폴링으로 기기간 갱신하고 오류 후 재시도한다. 환경별 요금과 백업 보존 범위는 계정 개설 시 확인한다.

## 4. 데이터 모델

ID는 UUID를 사용한다. 생성·수정 시각은 UTC `timestamptz`, 경기일과 기간 키는 서울 기준 `date`다. 월 키는 해당 월 1일, 주 키는 해당 주 월요일이다. 수량과 원장 금액은 정수이며 초과 입력은 서버에서 거부한다.

| 테이블 | 주요 컬럼과 제약 |
|---|---|
| `staff` | `auth_user_id` PK, `role`, `active`. 초대된 직원만 허용 |
| `members` | `id`, `nickname`, `nickname_key` UNIQUE, `created_at` |
| `game_types` | `id`, `name` UNIQUE, `active`, `current_version_id` |
| `game_rule_versions`, `game_rank_rules` | 게임 종류별 규칙 버전, `rank`, `points`, `buy_in_qty`, `ticket_qty`. 버전+순위 UNIQUE, 비음수 제약 |
| `games`, `game_results` | 경기일, 종류, 규칙 버전, 수정 버전. 결과는 경기+회원, 경기+순위 각각 UNIQUE. 점수와 프라이즈 수량 스냅샷 |
| `bingo_boards`, `bingo_cells`, `bingo_completions` | 월별 보드 UNIQUE, 보드+칸 번호 1~9 UNIQUE, 칸+회원 UNIQUE |
| `mission_templates` | 템플릿 ID, 이름, 활성화 기준 월, 표시 순서 |
| `mission_months`, `mission_month_items`, `mission_completions` | 월 키 UNIQUE, 월별 미션 스냅샷, 월·템플릿 UNIQUE, 월별 미션+회원 UNIQUE |
| `reward_settings` | 종류·단계별 프라이즈 이름. 주간 순위 및 별 기본값, 월간 프라이즈는 월별 스냅샷에 저장 |
| `star_missions`, `star_accounts`, `star_ledger` | 미션의 보관 상태, 회원별 비음수 잔액, 지급·차감·복구 원장. 원장에 미션 이름·변동량·실행자·요청 ID 기록 |
| `prize_payments` | 회원, 종류, 기간, 단계, 프라이즈/근거 스냅샷, 지급자, 지급 시각. 활성 지급 건에 아래 고유성 규칙 적용 |
| `audit_events` | 실행자, 변경 대상, 작업, 전후 값, 정정 사유, 요청 ID, 기록 시각 |

월간 미션·빙고의 활성 지급에 `(kind, period_start, member_id, milestone)` 부분 유니크 인덱스, 주간 랭킹 활성 지급에 `(kind, period_start, member_id)` 부분 유니크 인덱스를 둔다. 별 지급에는 요청 ID의 고유성을 강제한다. 기간 조회용 `games(game_date)`, 회원 검색·통계용 `game_results(member_id, game_id)`, 이력용 `prize_payments(paid_at)`, `star_ledger(member_id, created_at)` 인덱스를 둔다.

## 5. API 및 저장 경계

| 동작 | 계약 |
|---|---|
| 게임·게임 종류 | `GET/POST /api/admin/games`, `PATCH /api/admin/games/:id`, `GET/POST /api/admin/game-types`, `PATCH /api/admin/game-types/:id`. 경기 정정은 저장 당시 수정 버전을 요청에 포함 |
| 회원·매장 통계 | `GET /api/admin/members?from=&to=&q=`, `GET /api/admin/stats?period=&date=`. 기간과 검색 값을 서버에서 검사 |
| 빙고·월간 미션 | `GET/PUT /api/admin/bingo/:month`, `GET/PUT /api/admin/mission-templates`, `GET /api/admin/monthly-missions/:month`, 공통 달성 리소스 `PUT/DELETE /api/admin/completions/:kind/:itemId/:memberId` |
| 별 | `GET/POST /api/admin/star-missions`, `DELETE /api/admin/star-missions/:id`, `GET/POST /api/admin/star-ledger`. 지급에 회원·미션·개수·요청 ID 필요 |
| 프라이즈 | `GET /api/admin/prizes/pending`, `GET /api/admin/prizes/history`, `POST /api/admin/prizes/payouts`, `POST /api/admin/prizes/payouts/:id/void`. 지급에 대상 키·요청 ID, 취소에 사유 필요 |
| 손님 | `GET /api/public/display?view=&month=`. 화면별 공개 표시 데이터와 갱신 시각만 반환 |

- 조회 기간은 양 끝 날짜를 포함한다. 잘못된 날짜나 기간 역전은 400, 권한 없음은 401 또는 403, 버전 또는 중복 충돌은 409로 응답한다. 검증 오류는 필드별 한국어 메시지로 연결한다.
- 경기 쓰기는 경기와 모든 참가·결과·감사 이벤트를 한 트랜잭션에 저장한다. 지급은 요청 ID를 먼저 확인하고 현재 자격을 재계산한다. 동일 요청을 재시도하면 기존 결과를 반환한다.
- 별 지급·차감은 회원별 잔액 행을 잠근 뒤 잔액, 원장, 지급 이력을 한 트랜잭션에 기록한다. 잔액이 20이면 동시 요청 두 건 중 한 건만 성공한다. 잔액이 40이고 별개 요청 두 건이라면 두 건 모두 가능하다. 비별 보상은 DB 고유성 제약과 자격·기록 트랜잭션으로 중복을 막는다.
- 세션 쿠키는 보안 속성을 적용하고, 서버에서 직원 상태·역할과 쓰기 요청 출처를 검증한다. 공개 조회는 허용된 필드만 직렬화한다. 마이그레이션 계정, 앱 서버 계정, 테스트 계정을 분리하고 서버 전용 키를 브라우저 코드에 넣지 않는다.

## 6. 이관과 운영 준비

1. 개발·검증·운영 DB를 분리하고 마이그레이션으로 스키마와 초기 게임 규칙을 적용한다. 샘플 닉네임, 프라이즈, 지급 이력은 검증 환경에만 넣는다.
2. 이관 대상 브라우저가 있으면 `oceanspub-poc-v2` 데이터만 JSON으로 추출한다. `?sample=1` 데이터는 제외한다. 브라우저가 여러 대라면 어떤 데이터가 기준인지 정한 뒤 중복 닉네임·경기·지급·잔액을 먼저 대조한다.
3. 이관 도구는 미리보기 모드에서 회원 수, 경기 수, 달성 건수, 잔액, 지급 건수, 오류 목록을 출력한다. 이관 ID로 중복 실행을 검출하고 오류가 있으면 커밋하지 않는다. 기록 없는 잔액은 출처를 표시한 기초 잔액 원장으로 이관한다. 원본 파일은 접근이 제한된 위치에 보관한다.
4. 운영 전환 전에 초기 직원 초대, 실제 배점·프라이즈 설정, 공개 닉네임 확인, 백업과 시험 복구, 장애 시 로그 확인 및 이전 앱 버전 재배포 경로를 점검한다.
5. 운영 도메인에서 관리자 두 탭과 매장 표시 기기 한 대로 입력·갱신·지급을 확인한다. 운영 데이터가 적재된 뒤에는 스키마 호환을 확인하고 앱만 롤백하거나 후속 마이그레이션으로 정정한다.

| 순서 | 구현 단위 | 완료 기준 |
|---|---|---|
| 1 | 앱 골격, 환경 분리, PostgreSQL 마이그레이션, 인증·권한, 초기 검증 데이터 | 비로그인 관리자 조회·쓰기는 차단되고 공개 시작 화면은 열린다 |
| 2 | 회원 검색, 게임 규칙 버전, 경기 저장·정정, 주간 랭킹 | 순위 맞교환, 신규 회원 원자적 등록, 기록 정정, 과거 규칙 보존 검증 |
| 3 | 월간 빙고와 미션 템플릿·달성, 공개 화면 | 한 달 기록과 다음 달 기록이 분리되고, 3×3 빙고와 미션 6개 이상이 표시된다 |
| 4 | 별 원장과 프라이즈 지급·이력·색상 | 20개 차감·동시 지급·요청 재시도·색상 갱신·지급 취소를 검증한다 |
| 5 | 회원 및 매장 통계, 이관 도구, 운영 검증 | 기간별 집계와 인머니가 교차 검증되고 샘플과 운영 데이터가 분리된다 |

### 핵심 인수 시나리오

- 월요일 자정 직전·직후 경기와 월말·월초 기록이 정확한 기간으로 분리된다.
- 기존 경기의 순위만 바꾸면 그 경기의 규칙으로 재집계된다. 다른 관리자가 먼저 수정하면 덮어쓰기 대신 409가 반환된다.
- 1·4·5개 달성 단계는 별개로 지급되며, 빙고 3줄·올빙고도 별개로 기록된다. 취소·정정된 자격에 이미 지급된 건이 있으면 이력에서 확인할 수 있다.
- 같은 지급 요청을 재시도해도 한 행만 기록된다. 별 20개 잔액에서 서로 다른 동시 지급은 한 건만 성공하고, 두 기기에서 잔액과 이력이 일치한다.
- 관리자가 달성·지급을 저장하면 다른 기기의 게스트 화면에 폴링 주기 안에 반영된다. 이름 20명 이상은 빙고 칸과 별 구간에서 누락 없이 읽을 수 있다.
- 기간 조회에서 인머니, 승률, 방문 일수, 평균 상위 비율이 샘플 수기 계산과 일치한다. 공개 API 응답과 브라우저 데이터에 관리자 전용 정보가 포함되지 않는다.

### 운영 시작 전에 확정할 값

운영자 초대 계정과 운영 도메인, MTT 배점·순위별 프라이즈, 주간 랭킹 1~5위 및 별 교환 프라이즈 이름, 이관 대상 브라우저를 확정한다. 위 값은 관리자 설정 또는 운영 환경에 입력하며, 개발은 검증용 값으로 시작할 수 있다. 공동 5위 포함과 지난 주 정산을 기본 정책으로 채택한다. 실제 매장 규칙과 다르면 첫 운영 지급 전에 조정한다.
